# Retro: CalcFlow v1.0.0 Project Delivery

**Participants:** Eldad and Gavi

**Scope:** delivery through `v1.0.0 — Stable Final Release`
**Retro held:** 2026-08-02

## What happened

CalcFlow grew from a basic calculator into a tested scientific calculator:
editable expressions, powers, roots, logarithms, trigonometry with DEG/RAD,
history, memory, keyboard support, responsive layout, accessibility, logging,
exports, dependency and license evidence, CI/CD, and a published v1.0.0
release.

## What went well

- The team delivered in small, reviewable Feature PRs. Reviews caught real
  defects, including precision and sign-state errors, lost angle mode,
  accessibility semantics, responsive CSS behavior, and the Export Menu
  timeout race.
- QA was substantive: unit tests, linting, formatting, production builds,
  browser checks, regression checks, and Production smoke tests. Current
  verification: 288 tests, lint, formatting, and production build pass.
- Cross-feature fixes were generalized when needed. CFL-89 preserved angle
  mode across every `justEvaluated` continuation path rather than patching
  only the first failing action.
- Release evidence is traceable. Jira is complete, `main` is clean, and the
  non-draft `v1.0.0` GitHub Release is published.

## What to improve

- `SECOND_BRAIN.md` drifted behind live Jira and GitHub state. The final
  handoff still described CFL-31 as pending after the release was complete.
- Concurrent documentation PRs repeatedly conflicted on `SECOND_BRAIN.md`.
  Status documentation belongs with the Feature PR it describes, not in a
  separate companion PR.
- PR #66 merged before planned QA. Post-merge QA recovered the situation,
  but approval, QA, merge, and Done must remain separate gates.
- The same merge initially did not reach Production. A merge is not delivery:
  verify the deployed commit and smoke-test the live URL before marking work
  Done.

## Agreements for future work

1. Update each Jira item and `SECOND_BRAIN.md` at its actual transition;
   verify both before status reporting.
2. When work shares a reducer, layout shell, or handoff document, name one
   integration owner before parallel branches begin.
3. Complete and record QA before merging; an approval never substitutes for
   QA evidence.
4. Confirm the Production deployment serves the merged commit, then run a
   smoke test, before declaring delivery complete.
